#工学、キャッシュ、主権、ガベージコレクション

🧱 ブロックキャッシュガバナンスハブ（段落キャッシュ管理センター）

本ガイドは、Illacme Plenipes のブロックレベルシャドウキャッシュ（Block Cache Hub）の設計原理、物理ルータリングメカニズム、LRU ゴミ収集アルゴリズム、および自動クリーンアップ（Janitor GC）戦略について詳述しています。

🏗️ 1. 定義と物理ルーター (Definition & Physical Routing)

Block Cache Hub とは何か？

多言語出版および AI セマンティック翻訳パイプラインにおいて、ブロックレベルのシャドウキャッシュ（Block Cache Hub）は、元原稿内の各物理ブロック（Block）のハッシュ値と、それに関連する訳文・メタデータのマッピングを維持します。元原稿の微調整時においては、変更が発生したブロックのみに対してインクリメンタル翻訳をトリガーし、全量再計算を回避します。

物理ルーティング設計

段落レベルのシャドウキャッシュは、局所的な物理的隔離ストレージを採用しています：
- 設定ファイルパス：config.yaml または config.local.yaml にキャッシュハブ戦略が定義されています。
- 物理的永続化ライブラリ：現在の出版ブランドに対して、段落レベルのシャドウキャッシュの永続化データは imprints/{brand}/cache/block_cache.db または .cache/ ディレクトリに保存され、原稿ライブラリとは完全に物理的に隔離されており、ライブラリの純粋性を確保します。

⚙️ 2. LRU ゴミ収集とキャッシュ有効性検証アルゴリズム (LRU GC & Validation)

LRU ゴミ収集メカニズム

キャッシュハブは LRU (Least Recently Used) アルゴリズムに基づき、最も古いアクセスのないキャッシュ記録を淘汰し、物理ストレージを安全な水位内に維持します。
- アクセス更新：文書の段落がキャッシュに命中するたびに、その LRU タイムスタンプを現在時刻に更新します。
- 能動的解放：閾値を超えた場合、最も久しく使用されていない段落の翻訳を自動的に追放します。

段落有効性検証アルゴリズム (Block Validation Algorithm)

各キャッシュブロックは、ソースコードの段落内容から一意の SHA-256 ハッシュ値（Block Hash）を生成します。
検証フローは以下の通りです：
1. 文書を読み込む際、空行または物理マーカーに基づいて複数の段落に分割します。
2. 各段落ごとにハッシュ sha256(content + block_context_salt) を計算します。
3. キャッシュリポジトリ内の block_hash と比較します：
- 一致 (Hit)：既存の翻訳と段落属性を再利用し、LLM の再呼び出しは不要です。
- 不一致 (Miss)：「汚染ブロック（Dirty Block）」としてマークされ、翻訳待処理キューに投入され、元の位置にあるキャッシュは無効化されます。

🔄 3. キャッシュ追放と段落検証契約 (Eviction & Verification Rules)

キャッシュエビクションワークフロー（追放フロー）

### コンテンツ ###
[ドキュメントの変更] ──> [新しい段落のハッシュリストを計算] ──> [キャッシュマッピングと比較]
                                                │
                 ┌──────────────────────────────┴──────────────────────────────┐
                 ▼                                                             ▼
         [ハッシュ一致 (Hit)]                                               [ハッシュ不一致 (Miss)]
    キャッシュを再利用し、アクセスホットネスのタイムスタンプを更新                                   物理的に無効なキャッシュを排除 ──> AI 翻訳をトリガーして新しいキャッシュに書き込み

段落検証の三鉄則（Verification Rules）

  1. 構造破壊なし：翻訳対象の段落における Markdown マーク（太字、リンク、リスト、コードブロック）は検証時に等価なマークを保持し、形式の欠落を厳禁します。
  2. 文脈分離：ハッシュ計算時、前導および後続段落の一部のメタデータ（Block Context Salt）を組み合わせて、異なる文脈において同一の内容が曖昧さから不整合翻訳を生じることを防止します。
  3. 署名による改ざん防止：ローカル永続化データベース内のすべてのキャッシュ記録には Adler32 または SHA-256 のデータチェックサムが付与され、読み込み時に署名が無効な場合は物理損傷と判定し、自動的かつ自己修復を初期化します。

🧹 4. 自動クリーンアップ戦略と容量閾値 (Janitor GC ポリシー)

Janitor GC 自動クリーナー

システムに駐留する Janitor ガーディアンコルーチンは定期的にキャッシュ容量と物理使用率の監査を実行します。

容量と閾値ルール (Threshold Rules)

  • 物理ストレージ水位：単一ブランドの Block Cache 物理ファイルの占有上限はデフォルトで 128MB であり、80%（102.4MB）に達すると穏やかなクリーンアップがトリガーされます。
  • 段落数水位：総段落記録数の上限はデフォルトで 100,000 件 です。この閾値を超えると、Janitor GC が起動し、LRU のヒート（アクセス頻度）に基づいて末尾の 20% の期限切れシャドウキャッシュブロックに対して物理的な強制消去（Erase）を実行します。これにより、システムの軽量化と高応答性が確保されます。
  • 有効期限 (TTL)：90 日以内に読み込まれなかったか検証されなかった段落記録はすべて冷データ（Cold Cache）として判定され、GC サイクル中に自動的に空になります。
