🧱 ブロックキャッシュガバナンスハブ (Block Cache Hub)

本ガイドは、Illacme Plenipes のセグメントレベルシャドウキャッシュ（Block Cache Hub）の設計原理、物理ルーティングメカニズム、LRU ゴミ収集アルゴリズムおよび自動クリーンアップ（Janitor GC）戦略について詳述しています。

🏗️ 1. 定義と物理ルーティング (Definition & Physical Routing)

Block Cache Hub とは何か？

多言語出版および AI セマンティック翻訳パイプラインにおいて、段落級シャドウキャッシュ（Block Cache Hub）は、原稿内の各物理段落（Block）のハッシュ値と、関連する訳文・メタデータのマッピングを維持します。原稿の微調整時には、全量を再計算するのではなく、変更が発生した段落のみに対してインクリメンタル翻訳をトリガーし、無駄な計算リソースを防ぎます。

物理ルートの設計

コンテンツ

セグメントシャドウキャッシュは局所的な物理的隔離ストレージを採用します：

  • 設定ファイルパス：config.yaml または config.local.yaml にキャッシュハブ戦略が定義されています。
  • 物理永続化ライブラリ：現在の出版ブランドに対して、セグメントシャドウキャッシュの永続化データは imprints/{brand}/cache/block_cache.db または .cache/ ディレクトリに保存され、原稿ライブラリとは完全に物理的に隔離されており、ライブラリの純粋性を確保します。

⚙️ 2. LRU ゴミ収集とキャッシュ有効性検証アルゴリズム (LRU GC & Validation)

LRU ゴミ収集メカニズム

キャッシュハブは LRU (Least Recently Used) アルゴリズムに基づき、最も古くアクセスされていないキャッシュレコードを淘汰し、物理ストレージを安全な水位内に維持します。
- アクセス更新：文書の段落がキャッシュに命中するたびに、その LRU タイムスタンプを現在時刻に更新します。
- 能動的解放：閾値を超えた場合、最も長くアクセスされていない段落翻訳を自動的に追放します。

段落有効性検証アルゴリズム (Block Validation Algorithm)

各キャッシュブロックは、ソースコードの段落内容から一意の SHA-256 ハッシュ値（Block Hash）を生成します。
検証フローは以下の通りです：
1. 文書を読み込む際、空行または物理マーカーに基づいて複数の段落に分割します。
2. 各段落ごとにハッシュ sha256(content + block_context_salt) を計算します。
3. キャッシュリポジトリ内の block_hash と比較します：
- 一致 (Hit)：既存の翻訳と段落属性を再利用し、LLM の再呼び出しは不要です。
- 不一致 (Miss)：ブロックを「汚染ブロック（Dirty Block）」としてマークし、翻訳待処理キューに投入するとともに、その位置にある既存のキャッシュを破棄します。

🔄 3. キャッシュ追放と段落検証契約 (Eviction & Verification Rules)

キャッシュエビクションワークフロー（Eviction Flow）

                                                │
                 ┌──────────────────────────────┴──────────────────────────────┐
                 ▼                                                             ▼
         [ハッシュ一致 (Hit)]                                               [ハッシュ不一致 (Miss)]
    キャッシュを再利用し、アクセスヒートタイムスタンプを更新                                   物理エビクションでキャッシュを無効化 ──> AI 翻訳をトリガーして新しいキャッシュに書き込み

段落検証の三鉄律（Verification Rules）

  1. 構造破壊なし：翻訳対象の段落における Markdown 記法（太字、リンク、リスト、コードブロック）は検証時に同等のマークアップ記号を含める必要があり、フォーマットの欠落は厳禁です。
  2. 文脈分離：ハッシュ計算時には、前導および後続段落の一部メタデータ（Block Context Salt）を組み合わせることで、異なる文脈において同一の内容が曖昧さから不整合な翻訳を生じることを防止します。
  3. 署名による改ざん防止：ローカル永続化データベース内のすべてのキャッシュレコードには Adler32 または SHA-256 データチェックサムが付与されており、読み込み時に署名が無効化された場合は物理損傷と判定され、自動的に自己修復が初期化されます。

🧹 4. 自動クリーンアップ戦略と容量閾値 (Janitor GC ポリシー)

Janitor GC 自動クリーナー

システムに駐留する Janitor ガーディアンコルーチンは、定期的にキャッシュ容量と物理使用率の監査を実行します。

容量と閾値ルール (Threshold Rules)

  • 物理ストレージの水位線：単一ブランドの Block Cache 物理ファイルの占有上限はデフォルトで 128MB であり、80%（102.4MB）に達すると穏やかなクリーンアップがトリガーされます。
  • 段落数の水位線：総段落記録数の上限はデフォルトで 100,000 件 です。この閾値を超えると、Janitor GC が起動し、LRU のヒートに基づいて末尾の 20% の期限切れシャドウキャッシュブロックに対して物理的な強制消去（Erase）を実行します。これにより、システムの軽量化と高応答性が確保されます。
  • 有効期限 (TTL)：90 日以内に読み取られなかったり検証されなかったりする段落記録はすべて冷データ（Cold Cache）として判定され、GC サイクル中に自動的に空になります。
