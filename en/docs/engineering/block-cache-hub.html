🧱 Block Cache Governance Hub (Paragraph-Level Shadow Cache)

This guide details the design principles, physical routing mechanisms, LRU garbage collection algorithms, and automatic cleanup (Janitor GC) strategies of Illacme Plenipes paragraph-level shadow caching (Block Cache Hub).

🏗️ 1. Definition & Physical Routing

What is Block Cache Hub?

In multilingual publishing and AI semantic translation pipelines, the Block Cache Hub is responsible for maintaining a mapping of hash values, associated translations, and metadata for each physical paragraph (Block) in the source manuscript. It triggers incremental translation only for modified paragraphs during source manuscript adjustments, avoiding full recomputation.

Physical Routing Design

Paragraph Shadow Cache employs localized physical isolation storage:
- Configuration File Path: The cache hub strategy is defined in config.yaml or config.local.yaml.
- Physical Persistence Library: For the current publishing brand, paragraph shadow cache persistence is stored on disk at imprints/{brand}/cache/block_cache.db or under the .cache/ directory, fully physically isolated from the original manuscript library to ensure library purity.

⚙️ 2. LRU Garbage Collection and Cache Validity Verification Algorithm (LRU GC & Validation)

LRU Garbage Collection Mechanism

The cache hub evicts the oldest, unaccessed cache records based on the LRU (Least Recently Used) algorithm to maintain physical storage within a safe waterline.
- Access Update: Whenever a paragraph of a document hits the cache, its LRU timestamp is updated to the current time.
- Active Release: When exceeding thresholds, the system automatically evicts the longest-unused paragraph translations.

Paragraph Validity Verification Algorithm (Block Validation Algorithm)

Each cache block generates a unique SHA-256 hash value (Block Hash) from the content of its source code paragraph.
The verification process is as follows:
1. When reading a document, split it into several paragraphs based on empty lines or physical markers.
2. Calculate the hash for each segment sequentially: sha256(content + block_context_salt).
3. Compare with the block_hash in the cache library:
- Consistent (Hit): Reuse existing translations and paragraph attributes without re-invoking the LLM.
- Inconsistent (Miss): Mark as a dirty paragraph (Dirty Block), send to the translation pending queue, and discard the original cache at that location.

🔄 3. Cache Eviction and Paragraph Verification Contract (Eviction & Verification Rules)

Cache Eviction Workflow (Eviction Flow)

[Document Changed] ---> [Compute New Paragraph Hash List] ---> [Compare with Cache Mapping]
                                                │
                 ┌──────────────────────────────┴──────────────────────────────┐
                 ▼                                                             ▼
         [Hash Match (Hit)]                                               [Hash Mismatch (Miss)]
    Reuse cache, update access timestamp                                     Evict stale cache physically ---> Trigger AI translation and write to new cache

Paragraph Verification Three Iron Laws (Verification Rules)

  1. Structure Preservation: The Markdown markup (bolding, links, lists, code blocks) of the translated paragraph must be preserved during validation; equivalent formatting symbols are mandatory and format loss is strictly prohibited.
  2. Context Isolation: Hash calculation incorporates metadata from preceding and succeeding paragraphs (Block Context Salt) to prevent mismatches caused by ambiguity when identical content appears in different contexts.
  3. Signature Anti-Tampering: All cached records in the local persistent database include Adler32 or SHA-256 checksums; if a signature fails upon loading, physical corruption is deemed and auto-healing is automatically initialized.

🧹 4. Auto-Cleanup Strategies and Capacity Thresholds (Janitor GC Policy)

Janitor GC Auto-Cleaner

The resident Janitor daemon coroutine periodically audits cache capacity and physical occupancy rates.

Capacity and Threshold Rules (Threshold Rules)

  • Physical Storage Watermark: The default upper limit for physical file occupancy of the single-brand Block Cache is 128MB. A gentle cleanup is triggered when this threshold reaches 80% (102.4MB).
  • Paragraph Count Watermark: The default upper limit for the total number of paragraph records is 100,000. When exceeding this threshold, Janitor GC initiates a process to physically force erase (Erase) the last 20% of expired shadow cache blocks based on LRU heat, ensuring lightweight system operation and high responsiveness.
  • Expiration Time (TTL): Any paragraph record not read or verified within 90 days is classified as cold data (Cold Cache) and automatically cleared during the GC cycle.
